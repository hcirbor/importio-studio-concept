Method: static review, the existing quality/test suites, and axe-core 4.14.0 against the routes in `tests/routes.spec.ts` plus `/build` steps 1–4 at 1440×900 and 375×812. No application code, dependencies, markup, styles, or snapshot baselines were changed.

## 1. Summary

Overall health is **sound for a bounded mock demo, but not yet ready for a live engine**. The Phase 2 data source is reactive, persistent, covered by focused unit tests, and components do not import mock modules directly. The existing end-to-end and visual suites cover the main workflows and protect the current rendering. The main debt is concentrated rather than systemic: the engine boundary still transports presentation-ready UI models, several large components combine orchestration with rendering and parsing, and error/loading semantics are largely absent.

Top five risks:

1. **The engine contract is coupled to the current UI.** `RunEvent.presentation` and the workspace models carry display strings, tones, badges, and links. A live engine would either have to manufacture UI copy or force a breaking contract change.
2. **Live failures have no first-class path.** Engine promises have no shared loading/error/timeout model, run subscriptions have no structured failure payload, and several callers do not guard against rejection, duplicate submission, or late responses.
3. **Prompt interpretation is a fragile parser embedded in the composer.** Regex ordering, punctuation, and conjunction splitting can silently choose the wrong workflow or schema.
4. **Some workspace state still bypasses the data boundary.** The Home page's recent-pipeline rows are hard-coded, so they can disagree with workspace and review state.
5. **The accessibility scan found one critical rule family and four serious rule families.** The most urgent issue is tabs whose `aria-controls` targets do not exist.

## 4. Proposed cleanup for part B

### A. No visual change, no more than one day

1. Delete the 3 unused files and remove the 9 unused exports; set the quality baseline to zero.
2. Add selector-aware external-store subscriptions, then narrow consumers to the exact primitives/actions they need.
3. Add runtime decoders for localStorage and typed helpers for roles, field types, and route IDs; remove the listed unsafe casts.
4. Centralize field normalization/aliases/type inference and source-domain parsing, with table-driven unit tests.
5. Remove the unused `RunSession` props and `scenarioRunId` calculation.
6. Move Home recent-pipeline rows behind the data source so active-workspace state remains consistent.

### B. Component splits (rendered markup identical; visual tests required)

1. Split `workflow-composer.tsx` into a coordinator, pure parser/draft hooks, four stage components, and the monitor dialog as proposed in R14.
2. Split `run-session.tsx` into the browser frame, timeline, controls, capture history, and replay hook as proposed in R15.
3. Split `reference-sections.tsx` and `operate-sections.tsx` by exported page section/dialog as proposed in R16–R17.
4. Split discovery Search/Candidates/Qualify even though the module is now below 300 lines, because the three flows have independent state and responsibilities.
5. Split `workflow-scenario-review.tsx` (305 lines) into a review-record adapter/evidence mapper and a scenario-agnostic table view while preserving the exact DOM.

Each split should be its own small commit or PR slice, run the existing desktop/mobile screenshots, and accept **zero** baseline image updates unless Rob separately approves a visual change.

### C. Accessibility gate

1. Add axe checks to the existing Playwright route and build-step journeys at desktop and mobile.
2. Fail CI on any new `serious` or `critical` violation.
3. Record the five current rule IDs and their scoped selectors in a machine-readable baseline; make the checker reject additions and require the baseline to shrink when fixes land.
4. Fix without intended visual change first: invalid tab relationships, accessible-name mismatches, the empty brand image name, and the usage progress semantics.
5. **Rob decision required for possible visual change:** keyboard-focus affordances for `.table-scroll` and `.capture-strip` may add a visible focus ring; approve the focus treatment before updating visual baselines. The component splits themselves are not accessibility fixes and must not be used to conceal baseline changes.

### D. Deferred

1. **Engine/domain contract reshaping to Phase 4A.** R2 and the UI-built `WorkspaceRun`/`WorkspaceDataset` rows are explicitly contract work and should move together rather than be partially renamed now.
2. **Live loading/error/cancellation/timeout UX to the live-engine phase.** Define the engine error/progress model first, then add UI states before Phase 5 integration; doing isolated spinners now would encode the wrong contract.
3. **Prompt intelligence beyond deterministic mock planning.** Keep the current parser as a bounded suggestion with stronger tests; do not turn it into template-specific heuristics. A live planner should own semantic interpretation later.
4. **Potential visual accessibility changes.** Focus treatments and any layout needed for readable errors require explicit design approval and new visual baselines.
5. **`tailwindcss` dependency removal.** It is outside the tracked baseline and should be verified against the build configuration separately.
